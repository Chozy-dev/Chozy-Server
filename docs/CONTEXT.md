# Chozy Server 현재 상태

Chozy Server는 위탁 셀러의 상품 소싱 검증을 위한 REST API다. 현재 작업 범위는 Spring 서버이며 운영 연동은 후속이다.

## 구현 상태

| 범위 | 상태 |
| --- | --- |
| 공통 기반 | 공통 성공·오류 응답, 보안·CORS, OpenAPI, DB 없는 기본 프로필과 격리 PostgreSQL 개발 프로필 |
| 계정 | 개발용 일반 가입, 로그인, JWT 재발급·로그아웃, 회원 정보·비밀번호·광고 수신 동의 변경 |
| 마이페이지와 홈 | 대시보드와 무료 월간 분석 사용량 조회. 스크리닝·관심상품 집계는 저장 기반까지 구현 |
| 직접 입력 정밀분석 | 요청·예약·진행 조회, 작업 처리·만료, 리포트 저장·본인 조회·사용량 기록 경계 구현. 시장 데이터와 산식 엔진은 미연동이며 현재 요청은 503을 반환 |
| PostgreSQL | V1~V5는 기존 개발 DB 적용 이력 있음. V6는 직접 입력 분석 작업과 리포트 저장용이며 기존 개발 DB와 운영 DB 적용은 별도 |

## 구조

- Java 21/Spring Boot 모듈형 모놀리스다. `common`에 공통 웹·보안 설정을 두고 `auth`, `member`, `home`, `usage`, `analysis`에서 각 기능을 담당한다.
- JWT로 회원을 식별하고 업무 데이터의 소유권을 확인한다. PostgreSQL의 `chozy` 스키마에서 Flyway로 버전을 관리한다. 자체 데이터는 별도 저장소와 트랜잭션 경계를 사용한다.
- `analysis`는 작업 접수와 상태·리포트 저장을, `ManualAnalysisEngine`은 시장 데이터 조회와 리포트 계산 경계를 담당한다. 완료된 리포트는 기존 `usage` 원장과 함께 커밋한다.

## 최신 검증

Maven 기본 테스트 34개와 격리 PostgreSQL 16 통합 테스트 52개를 통과했다. V6 적용, API 수락·회원 격리, 마지막 슬롯 경합, 작업 만료, 차감 실패 시 롤백, 데이터랩 면제, 엔진 미등록 응답을 검증했다.

## 개발 순서

**다음 작업은 1번의 리포트 상세 계약과 최근 정밀분석 기록이다.** 기능 간에 공유하는 데이터와 API를 먼저 완성하고, Spring이 소유하는 데이터는 개발 PostgreSQL에서 검증한다. 외부 응답이 필요한 흐름은 테스트 픽스처로 계약을 검증하고 실제 연동 상태는 별도로 기록한다.

| 순서 | 구현 범위 | 완료 기준 |
| --- | --- | --- |
| 1. 정밀분석과 리포트 읽기 | 현재 직접 입력 접수·상태 조회를 기반으로 `GET /search/reports/{reportId}`의 필드·nullable 규칙을 명세에 맞추고 `GET /search/analyses/recent`를 추가한다. 이어서 리포트 점수 의견 저장을 구현한다. | 본인 스냅샷과 최근 기록의 조회 조건·정렬·페이징을 명세대로 검증한다. 직접 입력과 URL 분석이 이후 조회 계약을 공유할 수 있도록 하고, 조회·의견 저장 전후 사용량이 동일한지 확인한다. V6부터 격리 DB에서 이전 버전 업그레이드를 검증하고 기존 개발 DB 스모크는 별도 확인한다. |
| 2. 관심상품과 알림 | 리포트 ID로 관심상품을 등록한 뒤 목록·상세·상태 변경·판매 결과 기록·삭제를 구현한다. 알림 설정, 목록과 개별·전체 읽음 처리를 이어서 구현한다. | 본인 리포트만 관심상품으로 등록할 수 있고 중복·한도·상태 전이를 검증한다. 알림 설정과 읽음 상태를 회원별로 저장한다. 공급가·재입고 같은 외부 이벤트 알림의 생성은 연동 단계에서 확인한다. |
| 3. 검색과 분석 API 계약 | 스크리닝 요청·최근 기록, 쇼핑인사이트 분야·쇼핑 반응, 상품 URL 판별·URL 분석 요청, 쿠팡 카테고리, 리포트 추가 입력·재계산 순으로 계약을 묶는다. 이어 홈의 공급 추천·쿠팡 베스트·네이버 시즌·비교 조회 계약을 정리한다. | 쇼핑 반응은 선행 스크리닝 결과, URL 분석은 판별 결과, 재계산은 저장 리포트와 유효한 카테고리·옵션을 사용한다. 지원하는 계산 및 데이터 경로에 대해 Swagger와 계약 테스트를 맞추고, 변경 항목만 재계산하며 기존 리포트 수정은 무료 횟수를 차감하지 않는다. |
| 4. 실제 데이터와 계산 연결 | 직접 입력에 시장가·수수료·검색광고·데이터랩 및 분석 산식을 연결한다. 이어 스크리닝, URL 소싱처, 홈 발행 조회에 실제 데이터를 연결한다. Collector 구현·운영 전환 일정은 별도다. | 실제 데이터로 리포트와 진행 단계를 확인하고 호출 한도, 캐시, 필드 누락, 실패·재시도, 데이터랩 소진 시 차감 면제를 검증한다. 홈 조회는 발행 완료본 단위로 확인한다. |
| 공개 전 계정과 운영 검증 | 회원탈퇴·토큰 무효화, 휴대폰 본인인증·DI, 소셜 계정 정책, 운영 DB 역할과 배포를 점검한다. 계정 정책 설계는 앞 단계와 병행할 수 있다. | 탈퇴 후 기존 토큰 접근 차단과 개인정보·재가입 정책을 검증한다. 운영 데이터·계정과 외부 연동의 실제 적용 상태를 확인한다. |

각 API는 기획서와 원본 명세의 인증·입력·성공 응답부터 확인하고, 실제 구현과 오류·소유권 테스트를 함께 갱신한다. 명세에 빠진 경합·오류 계약은 선택한 동작과 근거를 BACKEND에 남긴다. 실제 데이터 경로가 준비되기 전에는 외부 응답을 테스트에서만 대체하고, 실행 환경에서 처리할 수 없는 요청은 현재 정밀분석의 503 계약처럼 명시적으로 응답한다.

실행·환경 설정은 [README](../README.md), API 계약과 트랜잭션 규칙은 [BACKEND](BACKEND.md), 기획 원문은 [references](references/)에서 관리한다. 변경 작업마다 이 문서의 현재 상태·문제·다음 작업을 갱신한다.
